## 2026-11-06

Goal for the day: define the executor boundary so the engine no longer depends on the fake executor type, then close the first week with a review checkpoint and no new features beyond that boundary.

What actually changed: executor.py now defines an Executor protocol with three methods, prefill, decode, and release, and documents who owns what. The engine now depends on that protocol instead of the FakeExecutor class, so any object with those three methods can drive it. State changes during execution stay the executor's job, queue changes stay the scheduler's job, and the engine owns the order of a step plus the timing of release: it tracks every request the executor started work on and, after the scheduler update, calls release at most once for each tracked request that reached a terminal state, with one extra sweep at the end of run_until_complete for a request cancelled between steps. The fake backend holds no per request resources, so its release only records the request id in released_request_ids, and release is idempotent on the executor side as a second safety net. A waiting request cancelled before prefill is never tracked and needs no release, because it never held backend resources. Added tests/test_executor_contract.py with eight tests covering a custom executor that shares no code with the fake backend, release exactly once for finished requests, no release while a request is still active, release for a running request cancelled between steps including when no further step runs, no release for a waiting cancellation, and idempotent fake release. The executor contract, a responsibility table, the failure rule (an executor error propagates, no terminal state is invented, and there is still no FAILED state), and the first week checkpoint were added to docs/design.md, and the verbose demo engine now follows the same track and release flow as the base engine.

Commands and observed results: `.venv/bin/python -m pytest -q` reported 54 passed in 0.07s, exit code 0, which is the previous 46 tests plus the 8 new contract tests. `.venv/bin/python benchmarks/demo_scheduler.py` exited 0 and again finished 3 requests in 5 steps with the same outputs as before. `.venv/bin/python -m mypy src/miniserve` reported success with no issues in 5 source files. `.venv/bin/python -m ruff check src/miniserve/engine.py src/miniserve/executor.py tests/test_executor_contract.py benchmarks/demo_scheduler.py` reported all checks passed.

One thing I can now explain: swapping in a real model backend only means implementing prefill, decode, and release against the same contract, because the scheduler never talks to an executor and its admission, budget, and cancellation rules do not mention a backend type. I can also explain one full engine step in my own words. One engine step works like this. The scheduler goes first: it prunes any request that already reached a terminal state, then it picks decode work for running requests before any new prefill, because requests already generating should not starve behind new arrivals, and it admits waiting requests in arrival order only while both the batch size limit and the per step token budget still have room. The engine hands the two selected lists to the executor, which is the only component that changes request state during execution: prefill moves a new request from waiting through prefilling to decoding and creates its backend state, and decode appends exactly one token to each running request, finishing any request that reaches its output limit. The engine then asks the scheduler to update the queues, which moves the new prefill requests into the running list and prunes anything that finished or was cancelled during execution. Finally, the engine releases backend resources for tracked requests that reached a terminal state, so a real backend would free their cache here, and it counts the step as done. If the queues are still non empty, the next step repeats the same order with the updated state.

Still unsure: there is still no FAILED state or failure reason, because there is still no real execution failure path to test one against, and resident cache capacity is documented as distinct from the per step budget but not yet enforced. Both are recorded in the checkpoint in docs/design.md and neither blocks the metrics work that comes next.

## 2026-11-08

Goal for the day: add a serial execution baseline that reuses the same requests, executor, and stopping rules as the continuous scheduler, then fix the workloads both schedulers will share so experiments are deterministic.

What actually changed: added SerialScheduler to scheduler.py. It subclasses the continuous Scheduler, so admission, validation, cancellation, and duplicate id rules are inherited and not reimplemented, and it changes only the selection policy: at most one request is ever active, no prefill is selected while a request is running, and only the head waiting request is prefilled when nothing is running. Added create_scheduler as the single configuration switch, where continuous returns a Scheduler, serial returns a SerialScheduler, and any other policy value raises ValueError. No second engine was copied; one Engine drives either scheduler. Added tests/test_serial_scheduler.py with seven tests covering the factory, the unknown policy error, one prefill in the first step, no prefill during decode, hand counted serial steps, the same output lengths and generated tokens under both policies, and reuse of the admission and cancellation rules. For the demo request set the serial run took 12 steps and the continuous run took 5 steps, with identical output lengths 4, 2, and 3; those step counts are simulation scheduling counts, not model throughput. Also added src/miniserve/workload.py with a deterministic seeded workload generator. Each WorkloadRequestSpec carries the request id, the exact prompt token ids, the output limit, and the arrival time, and can build a fresh Request with that arrival time on every call. Three profiles are defined: short with prompt 4 to 16 and output 2 to 8, mixed with prompts alternating short and long by position and output 2 to 16, and long_output with prompt 8 to 32 and output 24 to 48. Arrival times start at 0.0 and never decrease. Added tests/test_workload.py with eight tests covering same seed determinism, different seed variation, unknown profile and bad count errors, specification fields, the three profile shapes, default workload coverage, both schedulers reading the same workload with identical results, and fresh request copies. Saved benchmarks/workload_example.json with seed 1234 and six requests per profile as a worked example. The design document gained a section on the serial baseline and the policy switch and a section on deterministic workloads.

Commands and observed results: `.venv/bin/python -m pytest -q` reported 78 passed in 0.14s, exit code 0, which is the previous 63 tests plus 7 serial scheduler tests and 8 workload tests. `.venv/bin/python benchmarks/demo_scheduler.py` exited 0 and again finished 3 requests in 5 steps with the same outputs as before. A direct comparison built from the same three request specifications reported serial 12 steps and continuous 5 steps, both with output lengths 4, 2, and 3. `.venv/bin/python -m mypy src/miniserve` reported success with no issues in 7 source files. `.venv/bin/python -m ruff check src/miniserve/scheduler.py src/miniserve/workload.py tests/test_serial_scheduler.py tests/test_workload.py` reported all checks passed.

One thing I can now explain: the serial baseline is fair because it is not a separate system; it inherits admission and cancellation, shares the request type, the executor, and the stopping rule, and differs only in which requests a step selects, so a step count difference can be attributed to the scheduling policy alone. I can also explain why a workload must be a list of specifications rather than a list of request objects: request objects carry mutable execution state, so replaying the same objects through a second scheduler would leak the first run into the second, while specifications rebuild fresh requests with the same ids, lengths, and arrival times every time.

Still unsure: arrival times are stored in the workload specifications, but the current engine admits every request at once and does not replay the timetable yet. Replaying arrivals belongs to the experiment pipeline work that follows, and until then no timing conclusion should be drawn from arrival values.

## 2026-11-09

Goal for the day: separate simulation time from wall clock time with a deterministic logical clock and explicit step costs, then build the experiment pipeline that runs a workload, saves the configuration and the raw results under a run id, and recomputes its summary from those raw files alone.

What actually changed: added src/miniserve/simulation.py with a SimulationClock that only moves when it is advanced, a SimulationCosts parameter pair (prefill charged per prompt token, decode charged per generated token, both in logical seconds), and a SimulatedExecutor that charges those costs on the shared clock while following the same state transitions as the fake executor. Costs inside one step accumulate one request after another; that serial work assumption is written down in the new docs/simulation.md together with its consequence, that the total logical duration of a run is its total work under the model whichever policy scheduled it. The runner replays workload arrival times, admitting each request at the first step boundary at or after its arrival and jumping the clock over idle gaps, and it records one timeline row per step with the logical start and end times, the prefill and decode ids executed, and the waiting and running ids at the step start. WorkloadRequestSpec.to_request now accepts an optional shared clock, and Engine.step now returns the scheduler output it executed, which is what the timeline records. A hand worked example with three requests (prompts 10, 5, and 5, arrivals 0, 0, and 1.0) is traced in docs/simulation.md and saved in benchmarks/simulation_timeline_example.jsonl: four steps, durations 1.5, 1.5, 1.0, and 0.5 logical seconds, and per request times to first token of 2.5, 3.0, and 3.0. Doubling the decode cost to 1.0 leaves the schedule identical and grows the total duration from 4.5 to 7.0, which is recorded as the standing check that durations belong to the cost parameters, not to the scheduler. Added src/miniserve/experiment.py plus the two command line entries benchmarks/run.py and benchmarks/summarize.py. One run writes a fresh directory under benchmarks/results named by its run id, holding config.json with the package version and the cost parameters, the raw per request and per step files for each policy, and summary.json with summary.md; an existing run id is refused with FileExistsError instead of being overwritten. The summarize entry recomputes the summary from the raw files only and reproduces the original exactly. The recorded example run simulation-short-seed1234 (short profile, seed 1234, six requests) finished all six requests under both policies with the same 30 output tokens; the serial policy took 36 steps and the continuous policy 12, both totalled 21.3000 logical seconds of work, and the continuous run showed the lower mean time to first token (9.2167 against 10.3167) and the higher mean latency (15.8167 against 12.3167), reported as observed under this cost model. The design document gained a section on simulation time and a section on the experiment pipeline, and docs/experiments.md describes the layout and the recomputation rule.

One thing I can now explain: step counts and durations answer different questions in a simulation, because the schedule is chosen by the scheduler and the token budget while the duration of each step is charged by the cost parameters, so doubling the decode cost changed every duration and no selection at all.
