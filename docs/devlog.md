## 2026-11-05

Goal for the day: make cancellation and duplicate requests safe, then check the scheduler budget boundaries with hand computed examples.

What actually changed: the scheduler gained a single cancellation entry point, cancel_request, which removes a waiting or running request from its queue and returns True, treats a repeated cancel or a cancel after finish as a no-op that returns False, and raises KeyError for an id the scheduler never admitted. ## 2026-11-06

Goal for the day: define the executor boundary so the engine no longer depends on the fake executor type, then close the first week with a review checkpoint and no new features beyond that boundary.

What actually changed: executor.py now defines an Executor protocol with three methods, prefill, decode, and release, and documents who owns what. The engine now depends on that protocol instead of the FakeExecutor class, so any object with those three methods can drive it. State changes during execution stay the executor's job, queue changes stay the scheduler's job, and the engine owns the order of a step plus the timing of release: it tracks every request the executor started work on and, after the scheduler update, calls release at most once for each tracked request that reached a terminal state, with one extra sweep at the end of run_until_complete for a request cancelled between steps. The fake backend holds no per request resources, so its release only records the request id in released_request_ids, and release is idempotent on the executor side as a second safety net. A waiting request cancelled before prefill is never tracked and needs no release, because it never held backend resources. Added tests/test_executor_contract.py with eight tests covering a custom executor that shares no code with the fake backend, release exactly once for finished requests, no release while a request is still active, release for a running request cancelled between steps including when no further step runs, no release for a waiting cancellation, and idempotent fake release. The executor contract, a responsibility table, the failure rule (an executor error propagates, no terminal state is invented, and there is still no FAILED state), and the first week checkpoint were added to docs/design.md, and the verbose demo engine now follows the same track and release flow as the base engine.

Commands and observed results: `.venv/bin/python -m pytest -q` reported 54 passed in 0.07s, exit code 0, which is the previous 46 tests plus the 8 new contract tests. `.venv/bin/python benchmarks/demo_scheduler.py` exited 0 and again finished 3 requests in 5 steps with the same outputs as before. `.venv/bin/python -m mypy src/miniserve` reported success with no issues in 5 source files. `.venv/bin/python -m ruff check src/miniserve/engine.py src/miniserve/executor.py tests/test_executor_contract.py benchmarks/demo_scheduler.py` reported all checks passed.

One thing I can now explain: swapping in a real model backend only means implementing prefill, decode, and release against the same contract, because the scheduler never talks to an executor and its admission, budget, and cancellation rules do not mention a backend type. I can also explain one full engine step in my own words. One engine step works like this. The scheduler goes first: it prunes any request that already reached a terminal state, then it picks decode work for running requests before any new prefill, because requests already generating should not starve behind new arrivals, and it admits waiting requests in arrival order only while both the batch size limit and the per step token budget still have room. The engine hands the two selected lists to the executor, which is the only component that changes request state during execution: prefill moves a new request from waiting through prefilling to decoding and creates its backend state, and decode appends exactly one token to each running request, finishing any request that reaches its output limit. The engine then asks the scheduler to update the queues, which moves the new prefill requests into the running list and prunes anything that finished or was cancelled during execution. Finally, the engine releases backend resources for tracked requests that reached a terminal state, so a real backend would free their cache here, and it counts the step as done. If the queues are still non empty, the next step repeats the same order with the updated state.

Still unsure: there is still no FAILED state or failure reason, because there is still no real execution failure path to test one against, and resident cache capacity is documented as distinct from the per step budget but not yet enforced. Both are recorded in the checkpoint in docs/design.md and neither blocks the metrics work that comes next.

## 2026-11-07

Goal for the day: define the timing metrics with an injectable clock, then implement per request statistics that can be traced back to raw timestamps.

What actually changed: added docs/metrics.md, which freezes the meaning of arrival, admission, prefill start, first token, last token, and finished, gives the formulas for queue time, time to first token, end to end latency, and time per output token, states how finished, cancelled, and unfinished requests are counted separately, and separates engine time from future client time. Request now takes an injectable clock, defaulting to monotonic time, and records admission and prefill start and last token times alongside the times it already kept, all from that one clock, so tests use a fake clock and never sleep. The scheduler records admission when it accepts a request. Added src/miniserve/metrics.py with a frozen per request record that carries the state, the finish reason, prompt and output lengths, all raw timestamps, and the derived values, plus JSONL export and a counter that keeps finished and cancelled and unfinished apart. A missing value is exported as null, never as zero: a one token request reports time per output token as null because there is no interval between two tokens, and an unfinished request reports latency as null. Added tests/test_metrics.py with nine tests, including the hand worked three token example from the metrics document, where arrival at 100, admission at 101, prefill at 103, and tokens at 105, 107, and 109 give queue time 3, time to first token 5, latency 9, and time per output token 2, exactly as calculated by hand. Added benchmarks/metrics_example.jsonl with three deterministic records, one finished, one single token finished, and one cancelled while waiting, all produced with fake clocks and labelled as simulation timing in the metrics document, not as model performance.

Commands and observed results: `.venv/bin/python -m pytest -q` reported 63 passed in 0.14s, exit code 0, which is the previous 54 tests plus the 9 new metrics tests. `.venv/bin/python benchmarks/demo_scheduler.py` exited 0 and again finished 3 requests in 5 steps with the same outputs as before. `.venv/bin/python -m mypy src/miniserve` reported success with no issues in 6 source files. `.venv/bin/python -m ruff check src/miniserve/request.py src/miniserve/scheduler.py src/miniserve/metrics.py tests/test_metrics.py` reported all checks passed.

One thing I can now explain: time to first token and end to end latency share the same starting point, the arrival time, but end at different events, the first token becoming available and the request reaching a terminal state, so one number cannot stand in for the other. I can also explain why time per output token is undefined for a single token request: it averages the intervals between tokens, and a single token has no interval, so reporting zero would invent a speed that was never measured.

Still unsure: the fake executor produces its first token in decode, while a real backend can produce the first token from prefill logits. The metrics document records that the source of the first token time must be revisited and documented when a real backend lands, so the definition stays honest instead of silently changing meaning.

Next single step: add a serial execution baseline that reuses the same requests, executor, and metrics, so scheduling strategies can be compared fairly.
